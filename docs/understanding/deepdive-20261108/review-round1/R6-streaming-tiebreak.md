## 1 结论

1. **谁错**：**A 的 10.83 dB 对应固定 50 帧视频条件，整段与分窗的时间映射不同**。A 用**一个固定的 50 帧嘴型 embedding** 同时喂 4 s 整段（caf 把 50 帧内插到 501 帧 ⇒ 80 ms/帧）和每个 2 s 窗（50→251 ⇒ 40 ms/帧）。用 A 自己的 `cv` 音频、自己的切窗代码，只把视频换成逐窗真实嘴型轨道：**+10.83 → +20.09 dB**（同一条命令、同一批窗口）。用真实嘴型但仍是"固定 50 帧"：**−13.18 dB**。A 的随机嘴型恰好落在中间，纯属运气。
2. **B 不算错，但口径偏乐观**：+18.20 dB 是在 **t=1.42 s 才开窗**（Studio 的首窗从 t=0 的静音开始，被 B 整个跳过）得到的。同一段流、同一 ckpt、同一个 warm 网格：连续嘴型索引 **+17.44 dB**，B 的 `rint` 索引 **+18.19 dB**（帧索引差 0.75 dB）；**把 Studio 首窗算进去是 +14.71 dB**。B 的 `--mode stitch` guard 扫描还有"被评区域随 guard 移动"的混淆（见 §4.3）。
3. **规范数字**（6 s 真实流，3×2 s LRS2 片段 + 10 ms 交叉淡化，Studio 从 t=0 开窗）：
   **`stitched vs whole` = +14.71 dB / r 0.9835 / 最大偏差 53.4% 峰值**；**剔除冷启动首窗 = +16.72 dB / 0.9895 / 28.5%**。4 s 流：**+14.14 / 0.9813 / 53.9%**，稳态 **+17.52 / 0.9913 / 20.7%**。
4. **guard 不是主因**。两种语义分开量：**"丢弃窗尾"（stitch，Studio 可调的就是这个）80→456 ms：14.51→16.71 dB（+2.2，非单调）**；**"多喂右上下文"（lookahead）：22.12→22.92 dB（+0.8，基本饱和）**。A 的 +3.9 dB 与 B 的 +1.55 dB 量的是两个不同东西。
5. **对齐不是 8.69 dB**。A 比的是"窗的最后 0.5 s（guard=0）"与"窗中 guard=250 ms"，混了 guard 与相位；按 Studio 的发出区 `[22720,30720)` 平移相位 ±250 ms，与整段一致性只在 **15.86–17.99 dB** 之间波动（**2.1 dB**），任两种对齐互相 **17.0 dB**（6 s）/ **17.1 dB**（4 s）。
6. **所测窗口方案具有不同输出**：同一 ckpt 的任意两种 2 s 窗方案彼此相差 13–19 dB（6 s；4 s 的 2 s 平铺 vs 整段到 23 dB）—— 2 s 无重叠平铺 vs 6 s 整段 = **18.66 dB**，Studio 拼接 vs 2 s 平铺 = **15.26 dB**。所以 14–17 dB 不是"拼接没做好"，而是 `cLNhw` 全窗统计 + 窗长依赖与所测输出差异相关；归因及总体上限有待更多实验。

## 2 口径定义

三个量（`x` 为整段流，`WINDOW=32000`、`HOP=8000`、`GUARD=1280`、`FADE=320`、`LEFT=WINDOW-HOP-GUARD=22720`）：

| 量 | 定义 | 参考怎么来 |
|---|---|---|
| `whole` | `y_w = f(x)`，整段一次前向（6 s⇒T=751 帧，4 s⇒T=501 帧，**远超训练时的 251 帧**） | `infer_file.extract` 同一条路径；已确认它**不做内部切块**（`infer_file.py:69-82` 直接 `audio_model(waveform, embedding)`） |
| `stitched` | 第 k 窗终点 `e_k = GUARD + (k+1)·HOP`（`app.js:622` 的相位；首窗 9280），窗 `[e_k-32000, e_k)`，取窗内 `[22720,30720)`，块间 0 重叠，块首 320 样本与上一窗 `pred[30720:31040)` 线性交叉淡化 | 与 `studio/server.py:OutputSlicer.take` 逐行同构 |
| `stitched_ref` | **2 s 无重叠平铺**：窗 `[2ks, 2ks+2s)`，整窗输出，hop=2 s，无 guard、无淡化 | 见下"要不要" |

**`stitched_ref` 要不要？** 要，但它**不是质量参考**。它把"窗长"与"hop/guard/淡化"分开：`stitched_ref vs whole` 只含**窗长/统计**失配（6 s 18.66、4 s 23.18 dB），`stitched vs stitched_ref` 只含**拼接机械**（6 s 15.26、4 s 13.66 dB）。两者同量级 ⇒ 换 hop/guard 省下的误差远小于模型本身的窗长依赖。它**不能**当"拼接本可以达到的上限"用：平铺的第 2、3 块从半途硬起，没有左上下文，自己也有瞬态。

**指标（全部 float64，两路都先去均值）**

```
a       = <e,s> / ||s||^2                     # 最优缩放（SI-SNR 对增益不变）
SI-SNR  = 10·log10( ||a·s||^2 / ||e - a·s||^2 )
r       = Pearson(e, s)
maxdev  = max|e-s| / max|s|                   # 峰值归一（本文主口径，与 A 的"55% 峰值"可直接比）
maxdev_rms = max|e-s| / rms(s)                # 附报，避免峰值被单个尖峰支配
```
归一化方式**必须写明**：本文表里的 `maxdev` 一律是**峰值归一**；`rms_ratio = rms(e)/rms(s)` 单独给，用来核 A 的"−1 dB 电平"说法。

**视频条件（这是本次仲裁的关键口径）**：2 s 窗用"窗内帧中心落在窗内的那 50 个 25 fps 嘴型裁剪"，整段用同一条嘴型轨道的前 150/100 帧，保证**同一条嘴型在绝对时间上对齐**。A 违反的正是这一条。

## 4 差异定位（逐项 是/不是 + 证据）

### 4.1 音频是不是同一段？——**不是同一段，且都不是真实长音频**

- `falcon_lrs2_2mix` 每条 **恰好 32000 样本 = 2.000 s**（`tt/mix` 3000 条，`mix.json` 里逐条 32000；`wave` 读出来也是 32000）。语料里**没有 >2 s 的条目**，所以"4 s / 6 s 流"只能拼。
- A：`cv` split 前 2 条硬拼到 64000（§4.7 自己写了"两段拼接成 4.0 s"，但 §摘要第 6 条只写"4 s 音频"，没写是拼的）；**join 处无淡化**。
- B：`tt` split 同一 source id 前 3 条硬拼到 96000；**join 处无淡化**。
- 我在规范实验里按要求给 join 加了 **10 ms 交叉淡化**（`canonical.py:load_stream`，join 记录在 `joins=[32000,63840]`）。**实测 join 淡化对 SI-SNR 无影响**：`probe5` 在 warm 网格上 硬切 join 17.49 vs 10 ms 淡化 join 17.40（差 0.09 dB，方向还略差，因为淡化制造了 10 ms 双人重叠）。
- 另一件不同的事：**20 ms 块间淡化**（`OutputSlicer` 的 `FADE=320`）实测也无效（14.71 vs 硬拼接 14.72）→ A 的"淡化只治咔哒不治内容"**成立**（但那是块间淡化，不是 join 淡化）。
- 结论：音频不同（不同 split、不同条数、不同长度），但这不是 7 dB 差距的来源（见 4.2/4.4）。

### 4.2 `whole` 是"整段一次前向"还是"逐 2 s 窗前向"？——**两边都是真整段，不是 bug；但"整段"本身是移动靶**

- 两边都走一次前向：A `C.run(a, emb, x)`（4 s），B `infer_file.extract`（6 s）。代码确认 `infer_file.extract` 不切块（`infer_file.py:69-82`），`Falcon_Contrastive.forward` 把整条波形直接送进 `encoder`（`:103-114`）。
- **但输出强烈依赖整段长度**：同一段音频，2 s 无重叠平铺 vs 6 s 整段 = **18.66 dB**，vs 4 s 整段 = **23.18 dB**。原因就是 30 处 `cLNhw`（全窗 GroupNorm）——窗里有多少秒，统计量就跨多少秒。
- 所以"整段"是产品自己的离线口径（评估协议），可以当参考；但它**不是**"模型对每时刻的真值"，不能把 14–17 dB 全算成拼接的错。

### 4.3 guard 语义：**A 测的是"丢弃窗尾"，B 主表测的是"多喂右上下文"**

| | 窗口 | 发出块位置 | guard 变大时 | 被评绝对区域 |
|---|---|---|---|---|
| A `stitch(GUARD,·)`（`xwin.py:44-60`） | 恒 2 s | `[WINDOW-guard-HOP, WINDOW-guard)` | 块在窗内**前移**，窗口跟着 `e=guard+k·HOP` **重锚** | **不变**（`abs_lo=HOP(k-1)`，与 guard 无关） |
| B `--mode stitch --anchor grid` | 恒 2 s | 同上 | 块前移，窗口**不动**（`first_end=32000`） | **随 guard 移动**（`low=first_end-guard-HOP`） |
| B `--mode lookahead` | **2 s + guard** | 固定 `[22720,30720)` | 窗口**变长**，左侧上下文固定 22720 | 固定单块 `[32000,40000)` |

- **是**：A 的 80→456 是"丢弃窗尾"语义；**不是**：B 主表（`--mode stitch`）虽然也是同一几何，但 grid 锚定让每个 guard 评的是**不同的一段 0.5 s**，所以 B 的 16.69–18.74 非单调、640 ms 的 `maxdev` 突然跳到 0.438，都是这个混淆造成的（我复跑重现了）。
- B 的 `--mode lookahead` 与 A 的扫描**不是同一个量**：前者是"窗口吃更多未来"，后者是"同一 2 s 窗里把块往前挪"。实测两者差 7–8 dB（22 vs 15），**不可并列**。
- 规范做法：guard 扫描固定**绝对块**（epoch 锚定），我两种语义都报（§5）。

### 4.4 对齐扫描：**A 混了 guard 与相位；B 的设计对，但只取了两点**

- A（`xwin.py:83-90`）：`p0 = fwd(x[0:32000])[-8000:]` = 窗口**最后** 0.5 s（guard=0，右边一点未来都没有）；`p1 = fwd(x[4000:36000])[-12000:-4000]` = 同一段绝对音频落在窗内 `[20000,28000)`（guard=250 ms）。**这是 guard=0 与 guard=250 ms 的单块比较，不是两种 Studio 对齐**（Studio 的发出区是 `[22720,30720)`，guard 恒 80 ms）。且探针里**没有 20 ms 淡化**。
- B（`--align-shifts 0,4000`）：整段网格平移，块永远在 `[22720,30720)` —— **设计正确**，只是只有 2 个相位、且没淡化。
- 规范做法：9 个相位（−250…+250 ms，步长 62.5 ms），块恒在 Studio 的 `[22720,30720)`，同一绝对区间 `[16000,64000)` 上两两比。结果见 §5.3：**两两最小 17.0 dB，vs whole 只在 15.86–17.99 波动**。
- 所以 A 的 8.69 dB **不是**"换窗对齐的代价"，是"guard 从 0 给到 250 ms 的代价"；真正的对齐敏感度是 **~17 dB（两两）/ 2.1 dB（整段一致性波动）**。

### 4.5 追加定位：A 的视频条件（决定性）

用 A 自己的 `cv` 音频、自己的 4 s 流、自己的切窗代码，**只改视频**：

```
video=random  4s : si=+10.83 r=0.9611 maxdev=55.2%   ← 完全复现 A
video=const   4s : si=-13.18 r=0.2142 maxdev=254.1%  ← 真实嘴型但仍是固定 50 帧
video=track   4s : si=+20.09 r=0.9951 maxdev=25.7%   ← 逐窗真实嘴型（Studio 的真实做法）
```
机制：50 帧 emb 喂 4 s 整段时，`NeuroSCNetFusion` 用 `F.interpolate(size=T_a)` 把它拉到 501 帧（**80 ms/帧**）；同一 emb 喂 2 s 窗时拉到 251 帧（**40 ms/帧**）。**同一条嘴型被放慢 2×**。随机裁剪没有时间结构，拉伸无害；真实嘴型有开合时序，拉伸直接改变分离结果。这些对照显示视频时间映射与输出差异相关；各因素的独立贡献仍需进一步实验。

- 跨相位的整段一致性波动 **2.1 dB**（6 s：15.86–17.99；4 s：16.85–19.26）。
- **任两种对齐互相 SI-SNR：6 s 最小 17.02 dB，4 s 最小 17.05 dB**（最差对是 −62.5 与 +62.5 ms 两个相位；`±250 ms` 相差正好一个 hop，是同一网格相位，不计）。
- 所以"换窗对齐差 **8.69 dB**"应改为"换窗对齐后与整段的一致性仍在 **16–18 dB**，任两种对齐互相 **~17 dB**"。

### 5.4 一行结论

> **实测**：Studio 拼接 vs 整段前向 = **+14.71 dB / r 0.9835 / 最大偏差 53.4% 峰值**（6 s，含冷启动首窗）；**+16.72 dB / 0.9895 / 28.5%**（去首窗）。4 s 对应 **+14.14 / +17.52 dB**。guard 80→456 ms 在"丢弃窗尾"语义下 +2.2 dB、在"多喂右上下文"语义下仅 +0.8 dB；换窗对齐 ±250 ms 只带来 2.1 dB 的整段一致性波动（两两 ~17 dB）。同一 ckpt 的任意两种 2 s 窗方案彼此相差 13–19 dB（6 s；4 s 到 23 dB），这些数值描述所测输入下的差异；`cLNhw`、窗口位置与拼接对误差的贡献需进一步分离。

**B 的两个实现细节**（不影响结论，但建议修）：

## 8 未解

1. **join 是合成事件**：LRS2-2Mix 每条恰好 2.000 s，4/6 s 流必然拼；join 所在块只有 11.5–14.4 dB，真实连续长音频没有 join，规范数字可能再高 1–2 dB。本轮无法消除。
2. **窗长依赖无法与"窗口长度"解耦**：`whole` 是 4 s/6 s（T=501/751），训练只见过 251 帧；要分离"窗长"与"全窗统计"需要 >2 s 训练，或按 `fix2.py` 把 `cLNhw` 换成 `LN_c` 后重测（本轮未做，CPU 上改 30 处 norm 需另开实验）。
3. **只有 CPU fp32**：A800 上 fp16/fp32 的窗口一致性未测；GPU 数值差异通常 <0.5 dB，但没实测就不写。
4. **统计量小**：单个 source id、3 条片段、11 块（4 s 是 7 块）；换源/换长度预计 ±1–2 dB。误差是否随窗数累积（A 的 G9）本轮最长 6 s，未验证。
5. **冷启动窗算不算"质量"**：它是 Studio 的真实行为（`LEFT_CONTEXT=1.42 s`，首窗前 22720 样本是静音），但用户只经历一次。本文两个数都报（14.71 / 16.72），文档采用哪个口径需 lead 定。
6. B 的 `--mode lookahead` 只评了跨 join 的单块 `[32000,40000)`（14.35 dB），是 9 块里最差的块之一；它的结论方向对，绝对值不宜当流级数字引用。
